## 1. PRODUCT

Advice for a Dollar is a **one-person advice service**.

A stranger submits a personal problem, pays **$1 minimum / pay what you want**, and receives a thoughtful response **personally written by the site owner, Farida**. The site also has a public/community side where visitors browse previously approved problems and their advice.

The idea behind it:

- People sometimes need to talk to someone who doesn't know them.
- Reading other people's problems and responses should make a visitor feel they are not alone.

**It should feel:** playful · pixel-art · internet-native · warm · slightly absurd · human.

**It must not feel like:** a clinical therapy platform, a SaaS product, or an AI product.

**Hard rules**

- There is **no AI-generated advice anywhere in the product** — not as a draft, not as a fallback, not as a "suggested reply" in admin, not as filler content in the archive.
- Nothing in the UI, copy, or animation may imply a bot is responding.
- Only one real human gives advice: Farida.
- The service is **not** therapy or professional psychological care and must never be described as such.

## 5. SECRET WORD + MAGIC LINK

Every submission gets a **private token** and a **user-created secret word**.

**Magic link**

- URL shape: `/a/:token`.
- Token generated with cryptographically secure randomness (e.g. 32 bytes, base64url). Never sequential, never derived from the submission ID.
- The link lets the visitor: view their submission, see whether it's answered, read the answer, send their one follow-up, and delete the submission.
- Tokens must not appear in analytics, logs, or `Referer` headers. Use `<meta name="referrer" content="no-referrer">` on token pages.

**Secret word**

- Created by the visitor during submission.
- Never displayed publicly; never shown in the archive, admin list previews, or any shared surface.
- Stored hashed (bcrypt/argon2), never plaintext.
- The confirmation page shows it once, alongside the submission, and tells the visitor clearly to save it.

**⚠️ Design tension you must solve and explain before coding:** the spec asks that the same secret word not be reusable in a way that creates ambiguity, but a properly salted hash cannot be checked for uniqueness or looked up. Propose a concrete approach and get approval. Suggested direction: **do not enforce global uniqueness.** Instead, scope the secret word to a single submission and require *two* factors for recovery (e.g. secret word + the approximate submission date, or secret word + optional email). Explain the trade-off in plain language.

**Lost magic link (`/recover`)**

- The visitor supplies their secret word (plus whatever second factor is approved).
- Response must be **uniform**: never reveal whether a submission exists, never confirm or deny by wording or timing. Always return the same message; if there is a match, deliver the link via the channel the visitor already gave (email) or show it only after the second factor verifies server-side.
- Rate-limit attempts per IP and per secret word.
- Keep the experience warm and playful — the bunny shrugs. It must not look like a corporate password reset.

## 6. SUBMISSION FLOW

1. **Write.** The writing interface is the dominant interactive element of the landing page and of `/ask`. Starting to write must be effortless — the textarea is focusable and visible without scrolling.
2. **Safety screening.** Runs **server-side, before payment**. See Section 7.
3. **Secret word.** Visitor creates it.
4. **Visibility.** "Publish it" or "Keep private". Both cost the same. Public submissions go through owner review before appearing anywhere.
5. **Payment.** $1 minimum, pay what you want. Suggested amounts: $1 / $3 / $5, plus a custom field.
6. **Confirmation.** Show magic link, secret word, the submitted problem, the bunny, what happens next, and expected response time.
7. **Waiting.** Farida answers. Expected time: normally within 24 hours, up to roughly 2 days depending on volume.
8. **Answer.** Visitor returns via magic link and reads it.
9. **Follow-up.** Exactly one follow-up message. This is not a chat and not a public comment system.
10. **Next actions.** Submit another problem · browse other problems · send the follow-up · say thank you · pet the bunny.

The visitor must always know what happens next, at every step.

## 7. SAFETY — HIGHEST-PRIORITY FUNCTIONAL REQUIREMENT

Server-side screening must detect:

- suicidal ideation / self-harm
- abuse or domestic violence currently in progress
- medical emergencies
- imminent danger to self or others
- situations involving a minor's safety

**When flagged:**

- Stop the normal flow immediately. Do not reach payment. Charge nothing.
- Never publishable, under any circumstance, ever.
- Show a warm but serious safety interstitial with **real crisis and hotline resources**.
- **No jokes, no character voice, no pixel mascots, no animation** on this screen. Plain, calm, respectful. This overrides every playfulness rule in this document.
- Mark the record so admin sees the flag prominently.

**Implementation:** `lib/safety/screen.ts`

```ts
{ flagged: boolean, category: string | null, confidence: number }
```

Start with a clearly organised, commented keyword/phrase ruleset (negation-aware, idiom-aware). Ship unit tests covering both true positives and false positives — for example, **"I'm dying of embarrassment" must not be flagged**, and "I don't want to be here anymore" must be.

Acknowledge in `NOTES.md` that a keyword ruleset will miss cases; the backstop is that **no submission is ever published without human approval**, and a flagged record can never be un-flagged into the public archive automatically.

## 11. PIXEL ART & VISUAL SYSTEM

The site should feel like a small indie pixel-art game, not a web form.

### 11.1 Palette

Define in `src/styles/theme.css`. **Use semantic names — do not name CSS variables after hex codes** (`--752445` is meaningless to read and impossible to re-theme):

```css
:root {
  --c-plum:  #752445;
  --c-rose:  #EA6993;
  --c-blush: #F8CAE4;
  --c-sage:  #CFDD9D;
  --c-fern:  #2F582C;
}
```

Then derive semantic tokens on top (`--bg`, `--surface`, `--text`, `--muted`, `--accent`, `--focus-ring`, `--border`) and re-map those for day/night. Components reference semantic tokens only, never raw brand colours.

### 11.2 Canvas sizes for the artist

All art is authored at **1× on a strict pixel grid** and only ever scaled by whole numbers (×2, ×3, ×4). Never scale by 1.5.

| Asset | Canvas (1×) | Typical desktop scale | Notes |
| --- | --- | --- | --- |
| Small UI icons (arrow, heart, lock, star) | **16 × 16** | ×3 → 48px | 1px transparent margin all round |
| Interface objects (envelope, key, coin, stamp) | **32 × 32** | ×3 → 96px | |
| Standard character idle (bunny, owl) | **64 × 64** | ×3 → 192px | figure ≈48–56px tall, anchored bottom-centre |
| Character + prop (frog at computer) | **96 × 80** | ×3 → 288px | |
| Hero scene (frog + desk + bunny together) | **160 × 96** | ×3 → 480px | |
| Envelope animation frames | **64 × 64** | ×4 → 256px | fixed frame size across the whole sequence |
| Logo / bunny head | **32 × 32** | ×2 → 64px | must stay readable at 16px favicon |
| Full-bleed background scene | **480 × 270** | ×3 → 1440 × 810 | see mobile note |

**Mobile note (390px):** the background scales ×2 on mobile, which shows only ~195 background pixels of width. The artist must keep the essential composition inside a **centred 192 × 270 safe zone**, with the outer edges holding only extendable scenery (sky, grass, wall) that can be cropped away without losing meaning.

### 11.3 Animation guidance for the artist

- Idle loops: 2–4 frames at ~6fps.
- Typing: 2 alternating-hand frames at ~10fps, plus a subtle 2-frame head bob.
- Blink: single overlay frame, fired randomly every 3–6 seconds.
- Keep every frame of a character on the same canvas size with an identical registration point (bottom-centre), so frames never jitter.

### 11.4 Export rules for the artist

PNG with transparency · exported at 1× only (never pre-scaled) · anti-aliasing **off** · no soft shadows or semi-transparent edge pixels · no gradients that introduce off-palette colours · limit to the 5 brand colours plus at most 2 shades each and one outline colour · either numbered frames (`bunny_idle_01.png`) or a horizontal sprite sheet with uniform frame width · consistent lowercase snake_case naming: `character_state_frame.png`.

### 11.5 Placeholder policy while art is in progress

Every character and background asset is a **draft**. Register all assets in one manifest (`src/pixel/assets.ts`) mapping id → dimensions → source, so replacing a draft is a one-line change. Placeholders must be flat colour blocks at the exact final dimensions with a visible `DRAFT` label in dev builds — never emoji, never stock SVG.

### 11.6 Day / night and reduced motion

Ship a day theme and a night theme, both visually checked. Respect `prefers-reduced-motion`: ambient motion, typing animation, particles, and the envelope sequence all reduce to a static or near-static state; the submission still completes and still reaches confirmation.

## 12. ANIMATIONS

### Typing animation
Alternating keyboard positions, subtle head movement, tiny note/`!` particles. Eases in when the visitor types, and returns to idle roughly **700ms** after typing stops.

### Envelope animation (~2.5s total)
Submission should feel like a small ceremony:
text becomes a letter → letter folds → letter moves into the envelope → envelope closes → wax-heart seal stamps → small particle burst → envelope hops and settles → confirmation appears.

Optional sound toggle (paper rustle, stamp). **Sound off by default**, preference remembered.

Critically: the animation must never block or delay the actual submission result. If the request resolves faster, the animation plays out; if it fails, fall back gracefully without losing the visitor's text.

### Ambient world
A living background based on the reference artwork Farida supplies (currently a draft — build it so it can be replaced). Keep it lightweight: **one shared `requestAnimationFrame` loop** for all sprites and ambient motion, pausing when the tab is hidden.
